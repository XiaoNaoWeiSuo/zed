# Lin 长时间运行内存增长排查

2026-11-10 · macOS / Apple Silicon · Lin 1.27.0，构建 `20261103.131541`，源码基线 `b3a9591614`。

**优先修复侧栏对已移除项目的引用，再修复文件监听的符号链接扇出，以及 Agent 历史的全文重复常驻。** 源码实验复现了两处独立的项目保活路径；文件事件放大和长会话恢复的内存增量也分别做了对照。生产进程峰值为 **17.1 GiB**，没有可用的分配栈，因此还不能将峰值按这三条路径拆分。

## 生产现场

- Lin 主进程运行约 30 小时。现场采样的 physical footprint 为 15.8–16.3 GiB，峰值为 17.1 GiB。一次采样的默认 malloc zone 有约 3,451 万块分配、14.3 GiB 已分配空间，主要压力来自 `Malloc Small`。`ps` 的 RSS 只反映当时驻留的页，会漏掉压缩或换出的部分。
- 当时有 9 个项目、约 65.4 万个索引条目，用户主目录占约 62.5 万个。同一进程从侧栏移除该项目后，持久化的会话关联已清除，约两分钟内 footprint 从 15.1 降到 14.6 GiB，默认 malloc zone 的分配量从约 13.0 降到 12.5 GiB。
- 移除后运行时仍报告 9 个存活项目。约 31 分钟后，主目录的索引已增长到 633,537 个条目，仍有来自该目录的 Git 探测日志。**这次操作没有让主目录的 worktree 停止运行**，因此前后差值不能用来估算完整的项目释放量。
- 现场进程未开启 `MallocStackLogging`，Instruments Allocations 也未能附加。现场数据能证明主进程的堆压力及项目仍在扫描；下面的受控实验用来定位具体代码路径。

## P0：移除项目后，侧栏仍持有项目

1. [项目头菜单](../../../crates/sidebar/src/sidebar.rs#L2596)渲染时拿到一组强引用 `Entity<Workspace>`，再将它们捕获进菜单构造闭包。[Popover](../../../crates/ui/src/components/popover_menu.rs#L396) 在布局时就把闭包存在 handle 里，即使菜单从未打开。[侧栏按列表行号缓存 handle](../../../crates/sidebar/src/sidebar.rs#L2264)，项目移除只触发重建；当原行号不再用于项目头时，旧闭包和 Workspace 仍在缓存里。
2. [侧栏的活动条目](../../../crates/sidebar/src/sidebar.rs#L149)也持有强引用。[切换活动项目时的同步逻辑](../../../crates/sidebar/src/sidebar.rs#L1185)在新项目没有 Agent 面板或可同步的活动条目时，可以留下旧条目。移除事件没有按 Workspace 身份清掉这个引用。

[移除 Workspace](../../../crates/workspace/src/multi_workspace.rs#L1412)会清除正常的持有和持久化关联，但上述引用仍能让 Workspace、Project 及 worktree 存活。[本地 worktree 持有后台扫描任务](../../../crates/worktree/src/worktree.rs#L1440)，因此侧栏条目消失后扫描仍可继续。

**复现：** 两个 GPUI 探针分别隔离了两条路径。第一个渲染两个项目头，从不打开菜单，移除行号未被复用的项目并重绘；只有清除对应菜单缓存后，Workspace 和 Project 的弱引用才失效。第二个从有活动终端的项目切换到没有 Agent 面板或活动条目的项目，再移除原项目；清空菜单缓存仍不释放实体，清掉旧活动条目后才释放。两例各跑过 20 个调度种子，现有的关闭窗口释放测试也通过。这证明两条路径都可以保活已移除项目；生产样本没有记录具体是哪一条引用在保活。

**修复建议：** 菜单闭包只捕获稳定项目键和弱引用，在打开菜单时从当前 MultiWorkspace 查询项目；按稳定身份管理 handle，并在项目头消失时回收。处理 `WorkspaceRemoved` 时，按被移除的 Workspace ID 清掉对应的活动条目和待激活状态，保留其他 Workspace 的有效选择。回归测试要保留窗口，覆盖从未打开菜单、行号复用和不复用、切换到没有活动条目的项目。断言被移除项目的弱引用失效，并验证后续文件事件不会再触发它的扫描。

## P1：符号链接放大文件事件，已删除的别名仍被使用

[扫描目录时](../../../crates/worktree/src/worktree.rs#L5587)，scanner 把目录符号链接登记到 `symlink_paths_by_target`，包括尚未展开的别名。[删除快照条目和解除监听](../../../crates/worktree/src/worktree.rs#L3429)没有同步删除这份登记。[规范化事件](../../../crates/worktree/src/worktree.rs#L4739)按目标前缀查找别名，为每个匹配的别名生成一个事件；如果原路径也属于 worktree，还会保留原事件。[事件处理](../../../crates/worktree/src/worktree.rs#L4851)在判断普通路径是否需要扫描之前，就会逐级探测 Git 根。

- 现场日志在约 16 分钟内出现 6,271 条来自 453 个别名路径的 Git 探测错误。这些路径经由 macOS 沙盒目录下的符号链接指向同一个仓库。移除主目录项目后仍出现类似错误。
- 受控的 `Worktree::local` + `FakeFs` 实验设扫描深度为 2，布置 64 个未展开别名。一个目标文件事件触发约 340 次元数据查询；删除别名目录、确认其已从快照移除后，仍约 340 次。使用同一文件系统重新建 scanner 后约 20 次。诊断用例跑过 20 个调度种子，13 个现有符号链接测试通过。
- 单独提取事件展开逻辑做分配计数：2,000 个不同目标路径、453 个别名生成 908,000 个事件，峰值分配约 215.5 MiB；无别名时生成 2,000 个事件，峰值约 0.25 MiB。这是单批合成实验，测的是事件展开的成本，不能换算成生产进程的堆占用。

**修复建议：** 在删除、重命名、重定向和子树刷新时，同步维护别名登记；在拼接别名路径及探测 Git 之前，跳过不需要处理的映射。保留已加载别名、显式扫描路径、外部目标和有效的 Git 元数据事件；不能直接用索引排除规则丢弃 `.git` 事件，否则会漏掉 Git 状态更新。回归测试覆盖删除、重定向、未展开别名以及裸仓库和 linked worktree；确认真实目标事件仍处理一次，历史别名数量不再决定元数据查询量。

## P1：恢复大型 Agent 历史时，完整文件文本被多处持有

[历史读取](../../../crates/agent/src/db.rs#L790)先完整解压，再反序列化 `DbThread`。[重放工具结果](../../../crates/agent/src/thread.rs#L2058)复制工具输出到 ACP 的原始输出，[重放编辑](../../../crates/agent/src/tools/edit_session.rs#L307)又把完整旧文本和新文本交给 [`Diff::finalized`](../../../crates/acp_thread/src/diff.rs#L314)。即使编辑器缓冲区和语法差异延迟构建，原文也已驻留。[实时工具结果路径](../../../crates/agent/src/thread.rs#L5046)也会克隆输出。[会话清理](../../../crates/agent_ui/src/agent_panel.rs#L4372)只按面板限制可安全重新加载的空闲会话数量，默认 5 个，未按内容大小设置全局预算。

**对照实验：** 11 月 6 日，用同一 release 二进制、相同项目、关闭语言服务器，在隔离实例启动约 50 秒时比较堆分配。最大历史的压缩体积约 9.9 MB，解压后约 182.7 MB，其中约 162.1 MB 是完整编辑前后的文件内容。实验只修改历史副本。

| 恢复内容                                            |           堆分配 |
| --------------------------------------------------- | ---------------: |
| 没有活动 Agent 会话                                 |  81,339,108 字节 |
| 恢复原始长会话                                      | 868,176,116 字节 |
| 恢复同一会话，仅清空 309 对 `old_text` / `new_text` | 402,157,828 字节 |

仅这 309 对文件全文就使堆多分配约 **466 MB**；清空后还有其他恢复成本。另一组相同的 7 个项目、约 3.34 万条索引中，有无选中历史的堆分配约为 451 MB 和 177 MB。这证明会话内容可以独立推高内存，不能据此认定生产峰值主要来自会话。

**修复建议：** 优先让原始输出和 diff 共享不可变的文件内容，或把历史工具输出拆成轻量元数据和按需读取的 diff 正文。兼容包含 `old_text` / `new_text` 的旧历史，保留查看差异、恢复编辑和回放能力。再为可重新加载的空闲会话加跨面板的字节预算，先逐出最久未用的会话；进行中的请求、草稿、待回答问题、权限交互和无法重新加载的会话不能被逐出。用相同历史跑恢复对照，并反复切换、重开会话，检查冷会话的堆分配及行为是否符合预期。

## 后续验证

1. **先验证生命周期，再测内存。** 在同一进程反复打开和移除大项目，保持其他项目和窗口开启。确认存活的 Workspace、Project、worktree 计数恢复到基线，已移除项目不再处理事件。用已分配堆量判断对象是否释放，同时记录 footprint；分配器保留的页不一定立即归还系统。
2. **观察队列压力，再加容量限制。** [原生监听通道](../../../crates/fs/src/fs_watcher.rs#L954)、[每个 worktree 的待处理路径](../../../crates/fs/src/fs_watcher.rs#L682)和 [扫描状态通道](../../../crates/worktree/src/worktree.rs#L1360)没有明确上限。待处理路径会合并重复项，扫描状态也会共享部分持久化快照结构；当前没有生产队列深度数据，不能认定积压已经发生。先记录队列深度、高水位和事件放大倍率。若需要限制容量，按受影响的根合并事件，超过上限转为重新扫描；保留完成信号，不阻塞原生回调。
3. **用分配栈补齐生产峰值归因。** 用可从启动时采集 Allocations 或 malloc 栈的隔离构建，分别运行大目录监听、长历史恢复和两者同时开启的负载。记录 physical footprint、已分配堆量、存活项目、事件队列和保留的会话正文大小；再以约 30 小时的代表性负载对比修复前后。比较预热后重复操作是否仍留下不断增加的存活对象与堆分配。
